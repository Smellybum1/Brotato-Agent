## 3. The three integration traps

Wave instances built (denominator for everything in this section): **1709**.

**Trap 1 -- `wave_time.elapsed_sec` resets on the final captures of a WON wave.**
Detection: within a same-wave block, the first capture whose `elapsed_sec` falls
more than 1.0 s below the running max starts a post-reset tail; the tail is cut
off and the wave ends at the last capture before it.
Wave instances showing the reset: **243 / 1709 (14.2%)**.
Because it fires only on victories, a naive last-minus-first duration would
differ systematically between the arm that survives and the arm that dies.

**Trap 2 -- captures continue after the wave timer expires.**
Wave instances with >=1 capture at `remaining_sec <= 0`: **1341 / 1709**.
Post-timer capture counts: median 46, p90 51, max 62.
**Instant treated as wave end: `t = wave_time.duration_sec` (the horizon T).**
Reason: T is the only wave-end instant that is IDENTICAL across arms and
independent of the outcome. Using the last capture would make the
normalising denominator a function of the treatment (a treatment-rescaled
outcome -- exactly the design-time lie that retired `damage_taken`'s cousins).
Samples past T are linearly interpolated to T and then dropped.

**Extraction cross-check.** Summed `player_damage` amounts vs the archive's own
`summary.damage_taken`, over every kept run: **368 / 368 runs agree exactly.**
That confirms both that the fast field extraction is lossless AND that
`damage_taken` is nothing but the gross sum -- it is reproduced to the unit by
adding up `player_damage` alone, with no healing term anywhere.

**Trap 3 -- death truncation.**
Wave instances ending in death: **79 / 1709**.

| statistic | truncated AUC | death-adjusted AUC |
|---|---:|---:|
| mean (n=79 death waves) | 0.1215 | 0.4194 |
| median | 0.0956 | 0.3609 |
| min | 0.0089 | 0.0468 |
| max | 0.4156 | 0.8770 |

Size of the correction: mean shift **+0.2979 AUC** on death waves.
Truncating rewards dying early; the death-adjusted number does not.

**Trap 3b -- how solid is the death label, and where does the extension bite?**

* Death is labelled from `result == defeat` on the FINAL wave instance of a run,
  then required to be consistent with the series (a wave whose captures reach
  the horizon with h>0 is un-labelled). Death waves whose last observed h is
  still > 0: **79 / 79** -- i.e. the killing blow usually lands between captures,
  so h==0 is NOT observable and the label must come from the run result.
* SURVIVED wave instances whose captures stop >5 s before the horizon: **235 / 1630**.
  For these the last observed ratio is HELD to T (median gap 48.4 s, max 82.8 s).
  That is an assumption, not a measurement, and it INFLATES the AUC of any
  wave instance that was actually cut short by the harness rather than won.
  It is stated here because it is the one place the integral is not observed.

## 5. Endpoint A -- death-adjusted HP-deficit AUC (LOWER IS BETTER)

`h(t) = HP/max_HP` while alive, `0` after death for the rest of the horizon;
`AUC = (1/T) * integral_0^T (1 - h) dt`, trapezoid on `wave_time.elapsed_sec`.

**Coverage filter (denominator, stated before any number below).** Of 1709 wave
instances, **235** stop >5 s before the nominal horizon T without a death.
Those split two ways, and the split matters enormously:

* **235 = CLEARED EARLY** (the run continued to another wave, or ended in
  victory). **Wave 20 ends when the boss dies, typically far short of its 90 s**
  **nominal duration_sec** -- so these are mostly WINS. They are KEPT, with the
  last observed ratio held to T. Dropping them would have deleted exactly the
  winning arm: dropping them moves the agent wave-20 mean AUC from **0.1272 (n=307)**
  to **0.2946 (n=75)** -- a 2.3x inflation produced purely by a filter.
* **0 = genuinely INCOMPLETE** (final wave instance of a run that neither won
  nor died -- harness/crash truncation). These are EXCLUDED.

Analysed set: **1709** wave instances. Death waves are never excluded -- their
tail is a real h=0, not a gap.

CAVEAT, stated because it is load-bearing: for a wave that ends early on a boss
kill, `(1/T)` with T = 90 s credits the remaining ~60 s at the player's final HP
ratio. That is a CHOICE. The alternative (integrating only to the actual wave
end) makes the denominator a function of the outcome -- a treatment-rescaled
endpoint. The fixed-T version is used precisely to avoid that, and it means
wave-20 AUC rewards both surviving and killing the boss fast.

## 7. Endpoint C -- healing reconstructed from the HP series

Method: any positive HP delta between consecutive captures INSIDE one wave
instance. Deltas straddling a `max_hp` change are excluded from the healing
total and reported separately -- a `max_hp` increase is not healing, and
`hp_ratio` moves when `max_hp` moves even with `hp` constant, which is why the
raw `hp` field (not `hp_ratio`) is differenced here.

| bucket | HP | share of attributed total |
|---|---:|---:|
| total healing (in-wave, max_hp stable) | 14441.0 | 100% |
| trickle candidate (delta<=1 with regen>0 or lifesteal>0) | 9947.0 | 68.9% |
| lump (delta>1, or delta<=1 with no regen/lifesteal) | 4494.0 | 31.1% |
| EXCLUDED: positive delta across a max_hp change | 2810.0 | (not counted) |

**UNATTRIBUTED FRACTION: 100.0% of all reconstructed healing.**

That is not a typo, and it is the honest answer. The archive CANNOT separate
the candidate sources:

* `hp_regeneration` and `lifesteal` are both per-tick trickles that land as
  +1 HP steps in exactly the same field. There is no per-source counter and no
  regen/lifesteal event in the stream (section 2), so the +1 steps can be
  bounded JOINTLY but never split. Modelling regen as `rate * dt` and
  subtracting it would require the game's regen-tick rule, which is not
  observable here -- inventing it would be a fabricated attribution.
* Consumable heals are lumps, but so is a single frame that merges several
  regen ticks when captures are sparse.

So: the trickle/lump SPLIT above is a decomposition of the HP series, NOT a
source attribution. **0% of healing is attributed to a specific mechanic with
evidence; 100% is unattributed at source level.** The load-bearing quantity --
total healing, hence net damage -- is measured; the breakdown is not.

Full-run healing spread (n=40): min 0, median 72, max 288.
This is the spread that makes a GROSS damage counter an invalid endpoint.

## 8. Endpoint D -- healing-consumable pickups

Consumable `id` census across captures (entity-frames, not pickups):

| id | entity-frames |

**No pickup event exists in the stream** (section 2 enumerates every event),
so a pickup would have to be inferred. `instance_id` is POOLED/RECYCLED in this

than substituting a proxy.

Other failure modes of the attempted method, for the record:
* Two identical consumables within the position tolerance are indistinguishable.
* Which consumable ids restore HP is a game-content fact, not a telemetry fact.
  Only ids containing `fruit` were treated as heals; the census above shows
  `consumable_fruit` is in fact the only consumable id in the whole era.

## 9. Endpoint F -- variance components for sizing

**Inferential unit = a SOURCE STATE (a save / build).** Ticks are never the
sample size; a wave instance is one observation, and repeated fixture trials
from the same save are nested within that source state.

**There is NO source-state / save identifier in the archive.** `summary.json`
carries only `config_id`, which takes ONE value (`well_rounded_d0_anyranged`)
across all 490 era runs -- a structurally-uninformative field, and useless as a
grouping key. The requested per-fixture means where several trials share a
source state therefore CANNOT be computed exactly.

PROXY used instead, labelled as a proxy: the ENTRY BUILD fingerprint observed at
the wave's first capture -- `(max_hp, hp_regeneration, lifesteal)`. Trials
resumed from the same save enter the wave with identical stats, so an identical
fingerprint is a NECESSARY, not sufficient, condition for a shared source state.
Distinct saves can collide on it; a collision INFLATES within-state SD and
DEFLATES between-state SD, so the between-state SD below is a LOWER bound.

## 10. What is NOT computable from this archive

* Source-level healing attribution (regen vs lifesteal vs consumable): no
  per-source counter, no heal event. See section 7.
* Consumable pickups as ground truth: inferred only, `instance_id` is pooled.
* Within-source-state variance where each save produced a single trial.
* Anything about a wave the captures never covered -- a missing wave is a
  missing denominator, not a zero.
